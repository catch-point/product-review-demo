# Storage: JSON-LD REST service

A Spring Boot service that stores the product review graph. Its API
definitions are in `src/main/resources`, and its seed data is in `scripts/seed`:

| File | How it is used |
|---|---|
| `db/schema.sql` | Applied by Flyway as migration `V1__Review`, exactly as written. Editing it after it has been applied fails validation, so put later changes in new migrations, like `db/migration/V2__journal_notify.sql` |
| `context.jsonld` | The JSON-LD context. It is served at `/context.jsonld`, and every request and response document uses it |
| `openapi.yaml` | The OpenAPI document, served at `/openapi.yml`. A test checks that the controllers implement exactly its operations |
| `scripts/seed/catalog.json` | The default seed data for `scripts/seed-products.sh`: 240 products across six categories, their owner, reviewers, reviews and replies |

People sign in with the Keycloak realm in `../identity`, whose tokens say
whether they are reviewers or owners. The service decides what they may do
from those roles and from who owns or wrote each row.

## Run

From the repository root, start everything (Keycloak and its database, this
service's database, MinIO for its images, this service on :8080 and the web
application on :3000):

```sh
docker compose up -d --build
```

Then call the API with a development token. The service accepts them only
when you opt in, with `DEV_TOKENS=true` in the repository root's `.env`
(then `scripts/stack.sh storage up`), as the seed scripts need too:

```sh
TOKEN=$(ROLE=owner storage/scripts/dev-token.sh olive@example.com)
curl -X POST localhost:8080/people -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/ld+json' -d '{"name": "Olive"}'
curl -X POST localhost:8080/products -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/ld+json' \
  -d '{"type": "Product", "name": "Aria Studio Headphones", "description": "Wireless headphones.",
       "category": ["Audio"], "brand": "Aria", "gtin": "00012345600012",
       "sku": "ARIA-100", "mpn": "ARIA-100-BLK"}'
curl localhost:8080/products?category=Audio&minRating=4
```

To run the service without Docker Compose, using throwaway Testcontainers
(PostgreSQL and MinIO) instead, run `./mvnw spring-boot:test-run`.

### VS Code

Open the repository root. Under **Tasks: Run Task**, the `Storage: …` tasks
start, stop, restart and follow the logs of the containers. They also back up,
restore and reset the data (the database and the images) and seed the sample
product catalog. Each task runs `scripts/stack.sh storage <command>`, which
you can also run from a shell.

The **Run and Debug** view has two launch configurations:

- **Storage: Debug (Docker services)** starts Keycloak, the storage
  database and MinIO in Docker, then runs the service in the debugger on
  :8081 (actuator on :9081) against them.
- **Storage: Debug (Testcontainers)** runs it on :8082 against throwaway
  PostgreSQL and MinIO containers.

## How it works

- **Authentication.** Requests carry a JWT bearer token from Keycloak (the
  identity project's realm `reviews`): signed with one of its keys, from its
  issuer, for the audience `storage`, and with a verified email. In
  development, with `REVIEWS_SECURITY_DEV_TOKENS` on (`DEV_TOKENS=true` in
  `.env`), HS256 tokens signed with `REVIEWS_SECURITY_JWT_SECRET` (from
  `JWT_SECRET` in `.env`) are
  accepted too (`scripts/dev-token.sh`, which takes `ROLE=owner` and
  `ADMIN=1`); the token's algorithm tells them apart
  (`config.BearerTokenDecoder`). The email claim identifies the
  caller, who registers once with `POST /people`. Reads are public.
- **Authorization.** The services decide each write from the token's role
  and the rows themselves, so there is nothing to keep in step with the
  data:

  | Write | Who |
  |---|---|
  | `POST /products` | owners (role `owner`); they then own the product |
  | `PUT`, `DELETE /products/{id}` | owners, of that product (`product.owner`) |
  | `POST /products/{id}/reviews` | reviewers (role `reviewer`), except the product's owner, once each (a second gets 409; find the first with `?author={person IRI}` and update it) |
  | `PUT`, `DELETE /reviews/{id}` | the review's author |
  | `POST /reviews/{id}/comments` | the product's owner, once (a second gets 409 naming the first; after deleting it they may reply again), even after the product is discontinued |
  | `PUT`, `DELETE /comments/{id}` | the comment's author |
  | `PUT`, `DELETE /people/{id}` | that person |

  Everyone else gets 403. Ownership is checked on the row after it is locked
  (`SELECT … FOR UPDATE`) and before the request's preconditions, so a
  stranger learns nothing from them and the owner cannot change in between.
  The admin realm role reaches `CurrentUser.isAdmin()`, kept for future use:
  no operation allows administrators more yet. A product whose owner was
  deleted can no longer be changed. `DELETE /products/{id}` soft-deletes the
  product: it leaves listings, direct reads, review collections and its
  owner's `owns`, and takes no new reviews (404). Its reviews and replies
  stay readable through their own IRIs, their authors may still change them,
  and its owner may still reply. A repeated DELETE by that owner succeeds
  with 204 without checking preconditions; anyone else gets 404.
- **Emails** are never shown, except to the person themselves in
  `GET /people/me`. They only match tokens to people.
- **Audit.** Each write transaction sets `app.actor = 'person:<id>'`, so
  `journal_write()` attributes every row change, and records the database
  role that made it. The journal is not exposed by the API. Only its owner
  can write it (through `journal_write()`) or skip it (`app.skip_journal`,
  for a migration: `V7__journal_skip_by_owner_only.sql`).
- **Database roles.** The superuser, `postgres` (`STORAGE_DB_PASSWORD`), only
  makes the schema's owner: `db/owner.sql`, run by the one-shot
  `storage-db-roles` container. That script creates `reviews_owner`, which
  is not a superuser (its one extra attribute is `CREATEROLE`, to create the
  service's role), sets its password, makes it the owner of the database,
  and gives it anything in `public` that another role owns, such as what a
  restore creates. Migrations run as `reviews_owner`, which owns the schema
  and the journal (`spring.flyway.user`, `STORAGE_DB_OWNER_PASSWORD`). The service
  connects as `reviews_service` (`spring.datasource.username`,
  `STORAGE_DB_SERVICE_PASSWORD`), which may read and write rows and do
  nothing else: no DDL, no triggers disabled, no writes to the journal and
  no access to Flyway's history. After every migration,
  `database.ServiceRole` creates that role if it is missing, sets its
  password and grants it exactly that, so tables added by later migrations
  are covered without naming it. In Docker the migrations run in the
  one-shot `storage-migrate` container (`ca.leighnet.reviews.migrate.Migrate`),
  the only one given the owner's password; the service runs with
  `spring.flyway.enabled=false`. Run elsewhere (the VS Code launch,
  Testcontainers), the service migrates at startup itself, still connecting
  as its own role; Testcontainers runs `db/owner.sql` too. Neither accepts
  the owner in the service's place: migrating fails when the service's role
  is unset or is the migrating role itself, and the service refuses to start
  when it is connected as a superuser, as a role with `CREATEROLE`,
  `CREATEDB`, `REPLICATION` or `BYPASSRLS`, or as the journal's owner or a
  member of it (`database.ServiceRoleCheck`), wherever it runs. `ServiceRoleIT`
  checks that a role that is not a superuser owns the schema, what the
  service's role cannot do, and both refusals.
- **Collections.** `/people`, `/products` and `/products/{id}/reviews`
  return a Hydra `Collection`, with
  `totalItems`, the page's `member`s and a `PartialCollectionView` whose
  `first`, `previous`, `next` and `last` links page with `limit` and
  `offset`. `/products` also describes its filters as a `search` IRI
  template. A review embeds its reply (`comment`); replies have no
  collection of their own.
- **Discontinued products.** A product's owner's `DELETE` stamps its
  `discontinuedDate`. It is then absent from `/products`, direct reads,
  review collections and the owner's `owns`; new reviews of it get 404.
  Its existing reviews and replies stay readable through their own IRIs,
  their authors may still change them, and its owner may still reply.
- **Images.** `POST /images` (multipart, field `file`) accepts JPEG, PNG,
  GIF and WebP. The format comes from the file's leading bytes, not its name
  or declared type, and the whole image must decode. SVG and other formats
  are refused with 415. What the image says beyond its pixels is removed
  first (`image.ImageMetadata`): EXIF (GPS location, camera, time), XMP,
  IPTC, comments, text chunks and anything after the image's end. Colour
  profiles, transparency, animation and a JPEG's EXIF orientation (as its
  only tag) stay, and the pixels are not re-encoded. The stripped bytes are
  what is decoded, stored and named. Images are objects named `<sha256>.<ext>` in MinIO's
  `review-images` bucket (`image.ImageStore`), so identical uploads share a
  URL and `GET /images/{id}` can be cached forever. Use the
  returned `id` as a Product's or Review's `image`: only these uploads
  are accepted (400 otherwise). The row keeps its path from the service's
  root, `/images/<sha256>.<ext>`, and responses name it as a URL on the
  address the request came to, as every other IRI, so it works from `:8080`
  and from the web application's `/api/storage` alike.
  - **The bucket** is private: the service streams each image from it, with
    its own headers (an immutable year of caching, the SHA-256 as ETag, a
    sandboxing content security policy), and answers `If-None-Match` with a
    tag without asking MinIO; `If-None-Match: *` matches only an image MinIO
    has. `HEAD` asks MinIO for the size alone. Ranges are not
    served: images are small, and the edge keeps them whole.
  - **Writes** are conditional (`If-None-Match: *`), so an image's bytes are
    never replaced, and of two identical uploads at once one creates it. An
    upload of an image already there copies it onto itself, which makes it
    uploaded now.
  - **Unused images stay** until pruned: deleting a product or review,
    changing its image, or never using an upload leaves the object. The
    service can't delete; `scripts/stack.sh storage prune-images` lists the
    images no product or review uses that were last uploaded more than 7
    days ago (`PRUNE_IMAGES_OLDER_THAN`), and `--yes` deletes them with
    MinIO's root credentials. The days allow for a review being written
    after its image was uploaded; nothing schedules it.
  - **The service's MinIO user**, `reviews-images`, may read, write and list
    the bucket, and nothing else: no deleting, no other bucket, no
    administration (`minio/init.sh`, run by the one-shot
    `storage-minio-init` with the root credentials; `ImageStoreIT` checks
    it). It is the S3 API alone, so any S3-compatible store would do.
  - **When MinIO is unreachable** uploads and image reads get 503 with
    `Retry-After`; everything else still works, and readiness is unaffected.
- **Caching.** Single people, products, reviews (with their replies),
  comments, categories and the email-to-person lookup are cached as
  database rows in Caffeine. A cache hit needs no database connection, and
  conditional `GET`s answer 304 from the cache too. Collections are not kept
  there. Over HTTP, single resources (with ETags) and collections (without)
  are `Cache-Control: no-cache` and the same for every caller, so shared
  caches may keep them and revalidate; only `GET /people/me` is `private`
  with `Vary: Authorization`. Anything else, errors included, keeps Spring
  Security's `no-store`, so a cache that believes it (the edge does) never
  stores it. Their IRIs
  are built from the request's address (`X-Forwarded-Host`, `-Proto` and
  `-Prefix`, from anyone), so a cache in front must key by it, or let only
  a proxy that sets it reach the service, as the Compose stack does: the
  presentation server names its configured `PUBLIC_URL`.
  Every change is evicted using the journal:
  - **This instance's own writes:** at commit, the service reads the
    transaction's journal entries and drops what they affect, so the next
    request sees the change.
  - **Everything else:** migration `V2__journal_notify.sql` sends a
    PostgreSQL `NOTIFY` for every journal entry, and each instance
    `LISTEN`s and drops the same entries. This covers other instances and
    changes made outside the service, such as with `psql`, within about a
    second.

  If the listener's connection drops, the caches are cleared. The 60-second
  time-to-live limits how long a rare race (a read that fills the cache just
  as a write commits) can serve stale data. Spring Boot Admin's **Caches**
  page and the `cache.gets` metric (`result:hit`/`miss`) show how well it
  works.
- **Concurrency.** Writes are optimistic. A `PUT` or `DELETE` sends the
  ETag it read as `If-Match`. If the resource has changed since, the write
  fails with 412 and changes nothing, so no one silently overwrites a change
  they never saw. A write without `If-Match` fails with 428:

  ```sh
  ETAG=$(curl -sI localhost:8080/products/1 | tr -d '\r' | sed -n 's/^ETag: //Ip')
  curl -X PUT localhost:8080/products/1 -H "Authorization: Bearer $TOKEN" \
    -H "If-Match: $ETAG" -H 'Content-Type: application/ld+json' -d @product.json
  ```

  - **Atomic check.** The service locks the row (`SELECT … FOR UPDATE`),
    reads it from the database rather than the cache, and checks the ETag
    in the same transaction as the change, so two writers holding the same
    ETag cannot both succeed. The lock also keeps `dateModified` increasing
    between writes, which the validators depend on.
  - **Chaining.** `POST` and `PUT` responses carry the new `ETag` and
    `Last-Modified`, with `Content-Location` naming the resource the body
    represents. A client can send that ETag with its next change without
    reading again.
  - **Weak tags.** RFC 9110 compares If-Match strongly, which a weak ETag
    never passes. These ETags identify versions, not bytes, so If-Match
    compares them weakly: `W/"x"` and `"x"` match.
  - **Other headers.** `If-Unmodified-Since` works too, but HTTP dates have
    whole seconds, so it misses a change made in the same second.
    `If-Match: *` accepts any version.
  - **Precedence.** 404 and 403 are reported before 412 and 428.
  - **Browsers.** CORS exposes `ETag`, `Last-Modified`, `Location` and
    `Content-Location`, so browser clients can read them.
  - **Caches in writes.** Inside a write transaction the row caches are
    bypassed, so a write never caches a row it might roll back.
- **Request limits.** No request makes the service read more than it
  needs. `web.RequestBodyLimit`, before authentication, refuses a JSON
  body over 64 KB (`reviews.requests.max-body-size`), or an upload over
  `reviews.images.max-size` plus 64 KB of multipart encoding, with 413:
  - at once, unread, by its `Content-Length`;
  - or, without one (chunked), as soon as reading passes the limit.

  Within that, every property has a `@Size`: IRIs and URLs at most 2000
  characters, at most 20 categories. Jackson reads no string longer than 20000
  characters, and nothing nested more than 32 deep (`spring.jackson.factory.
  constraints.read`); those fail with 400. Tomcat allows 8 KB of headers,
  5 parts to an upload, and 20 seconds between reads. Of a body it
  refuses unread, it reads at most 64 KB before closing the connection.
- **Rate limits.** `web.RateLimiter` gives each client a bucket a minute
  of 600 reads, 60 writes and 10 image uploads (`reviews.rate-limits`),
  checked before the request body is read. A signed-in person is counted
  by their email, wherever they connect from; anyone else by their
  address. Past a limit: 429 with `Retry-After`. The seed scripts wait
  that long and carry on.
  - **Client address.** The connection's peer, unless it is a trusted
    proxy (`reviews.requests.trusted-proxies`). Then it is the last address
    in `X-Forwarded-For` that is not one too (`web.ClientAddress`). In the
    Compose stack, only the presentation server is trusted, at its fixed
    address on the `backchannel` network; it names the address the edge
    (`edge/`) saw. Requests to storage's own published port come from the
    Docker gateway, so they cannot choose their address.
  - **One instance.** The buckets are in memory. Several instances would
    each count their own requests, unless an edge proxy (or a shared
    store) limits them.
- **Bounded work.** `offset` is at most 10000 (`Hydra.MAX_OFFSET`). At most
  one image per processor is decoded at a time, and an upload that waits
  5 seconds for its turn gets 503. A request that waits 5 seconds for a
  database connection, or a statement that runs 10, gets 503 with
  `Retry-After` (`spring.datasource.hikari.connection-timeout`,
  `spring.jdbc.template.query-timeout`).
- **Aggregate ratings** are recomputed from a product's reviews in the
  same transaction as each review change. Each rating is first scaled to
  1-5.

## Monitoring

Actuator runs on its own **management port, 8081**. In Docker that port is not
published to the host, but every container on the Compose network can reach
it, so it is locked down (`config.SecurityConfig`):

- **Open:** `/actuator/health`, with its status alone, and `/actuator/info`.
- **Everything else** needs the actuator's one account, `actuator` with
  `ACTUATOR_PASSWORD` (the repository root's `.env`, from
  `scripts/secrets.sh`), over HTTP Basic. Signed in, health shows its
  components too. Bearer tokens don't work there, and that account doesn't
  work on the API.
- **Read-only:** no endpoint may change anything, signed in or not, except
  `loggers` (log levels) and `caches` (clearing them), the two Spring Boot
  Admin acts through (`management.endpoints.access` in `application.yml`).

The API port serves just the probes, `/livez` and `/readyz`, which the
container's health check uses.

### Spring Boot Admin

`admin/` is a small [Spring Boot Admin](https://github.com/codecentric/spring-boot-admin)
server, run by Compose as `storage-admin`. The storage service registers with
it at startup, and hands it the actuator's account in the registration's
metadata (`user.name`, `user.password`), which it signs in to the actuator
with. Its UI shows that password masked.

- Open http://localhost:8095 and sign in as `admin` with `ADMIN_PASSWORD`
  (from the repository root's `.env`, generated by `scripts/secrets.sh`;
  `ADMIN_USERNAME` changes the name, and the service uses the same values to
  register).
- The `storage` instance shows health (database, the images' bucket as
  `images`, disk, probes), metrics,
  environment and configuration (secrets masked), loggers (change levels
  live), thread dumps, request mappings, beans, conditions, scheduled tasks
  and the Flyway migrations.

`scripts/stack.sh storage up` (or the VS Code task **Storage: Start**) starts
it too: `docker compose up storage` starts the `storage` service and what it
needs, but not `storage-admin`, and `--wait` would count the one-shot
containers (`storage-db-roles`, `storage-migrate`, `storage-minio-init`)
exiting as failures. Its port is `ADMIN_HTTP_PORT` (default 8095).

### Metrics from the command line

From inside the stack, call the management port directly, as the actuator's
account (the container has its password as `REVIEWS_ACTUATOR_PASSWORD`):

```sh
docker compose exec storage sh -c 'curl -s -u "actuator:$REVIEWS_ACTUATOR_PASSWORD" localhost:8081/actuator/metrics'
docker compose exec storage sh -c 'curl -s -u "actuator:$REVIEWS_ACTUATOR_PASSWORD" \
  localhost:8081/actuator/metrics/http.server.requests'
docker compose exec storage sh -c 'curl -s -u "actuator:$REVIEWS_ACTUATOR_PASSWORD" \
  "localhost:8081/actuator/metrics/http.server.requests?tag=uri:/products/%7Bid%7D&tag=method:GET"'
```

Or go through Spring Boot Admin's proxy, from the host:

```sh
set -a; . ./.env; set +a     # ADMIN_PASSWORD, from scripts/secrets.sh
ID=$(curl -s -u "admin:$ADMIN_PASSWORD" -H 'Accept: application/json' localhost:8095/applications \
  | jq -r '.[] | select(.name == "storage") | .instances[0].id')
curl -s -u "admin:$ADMIN_PASSWORD" localhost:8095/instances/$ID/actuator/metrics/jvm.memory.used
```

A metric returns `measurements` (for example `COUNT`, `TOTAL_TIME` in
seconds, and `MAX` for timers) and `availableTags`; filter with one `tag=` per
tag. The `uri` tag is the route template, so `{id}` must be URL-encoded.
Tags that match nothing recorded since the service started return 404.

| Metric | What it measures |
|---|---|
| `http.server.requests` | Requests by `uri`, `method`, `status`, `outcome` and `exception` |
| `hikaricp.connections.active` / `.pending` | Database connections in use, and requests waiting for one |
| `jvm.memory.used`, `jvm.gc.pause`, `jvm.threads.live` | Memory, garbage collection and threads |
| `process.uptime`, `process.cpu.usage` | The service process |

**Security.** The management port needs no token, so it must stay off the
public network. `heapdump` is not exposed, because a heap dump contains
secrets. Outside Docker, the service binds the management port on every
interface: set `MANAGEMENT_SERVER_ADDRESS=127.0.0.1` to keep it local.

## Test

```sh
./mvnw test      # unit and web-slice tests (JUnit, AssertJ, Mockito)
./mvnw verify    # plus integration tests with Testcontainers (needs Docker)
```

The integration tests run MinIO too, the Compose image with the bucket and
user `minio/init.sh` makes (`TestcontainersConfiguration`).

`./mvnw verify` also writes the coverage of both (JaCoCo) to
`target/site/jacoco/index.html`. `src/test/resources/application.properties`
turns development tokens on and the required-secrets check off for the tests
(and for `./mvnw spring-boot:test-run`).

The integration tests run the whole API against a PostgreSQL 18 container. They expand responses with a JSON-LD processor to
check that the documents mean what the context says.
